# Contributing

This project welcomes careful criticism, negative results, alternative models, security analysis, documentation, tests, and implementations.

## Before contributing

1. Read the project charter, non-goals, terminology, and quality gates.
2. Search existing issues and RFCs.
3. For significant changes, open a research question or RFC before writing substantial code.
4. State what evidence could prove the proposal wrong.

## Contribution categories

- **Editorial:** wording, examples, citations, formatting
- **Specification:** ontology, schema, invariants, protocol behavior
- **Research:** literature review, benchmark design, replications
- **Implementation:** runtime, adapters, validators, tooling
- **Security:** threat models, abuse cases, mitigations, audits

## Developer Certificate of Origin

Contributions must include a sign-off certifying the Developer Certificate of Origin 1.1:

```text
Signed-off-by: Your Name <your-email@example.com>
```

Use `git commit -s`. The DCO is published at https://developercertificate.org/.

## AI-assisted contributions

AI assistance is permitted, but the human contributor remains responsible for correctness, licensing, security, citations, and tests. Disclose material AI assistance in the pull request when it generated substantial text, code, schemas, or research summaries. Do not submit output that you have not independently reviewed.

## Research evidence

- Prefer primary sources, official specifications, standards, and original papers.
- Record the accessed version or publication date.
- Label preprints and unreviewed claims.
- Distinguish fact, inference, hypothesis, and project decision.
- Do not cite a source for a claim it does not support.

## Pull requests

A pull request should include:

- problem statement
- proposed change
- alternatives considered
- known risks
- validation performed
- compatibility impact
- security/privacy impact
- linked issue or RFC when applicable

Until a second maintainer joins, merges may be performed by the founder after automated checks and a documented self-review. Once multiple maintainers exist, high-risk changes should require independent review.
